USACE EMT modernization: public data and an APEX-to-custom-code demo plan

Which public datasets can stand in for CEFMS, EMS labor logs, P2/CMP and BUILDER, and how to stage a credible Oracle APEX to FastAPI + React demo on them.

Bottom line

None of the four internal systems the contractor named (CEFMS, EMS labor logs, P2/CMP, BUILDER) publish records. But every one of them has a credible public stand-in, and — the useful surprise — USACE already runs public, live Oracle APEX applications on ORDS (Corps Locks and NTNI at ndc.ops.usace.army.mil/ords, branded CWBI). That gives the demo a real "before": show the actual USACE APEX app, then show the same data re-served through a custom API and React front end, with the EMT-style enterprise/program/project roll-ups layered on top from USAspending, the Civil Works work plans, OPM workforce data, and the National Inventory of Dams.

APEX today vs. the custom-code target

The customer has confirmed EMT is Oracle APEX (the older public solicitation also mentions ColdFusion and JavaScript, and interfaces with CEFMS II, PROMIS and the Enterprise Data Warehouse). So the demo is APEX-specific: the "before" is a real USACE APEX app (Corps Locks), and the target keeps the Oracle database and ORDS while the page logic moves into a FastAPI service and a React front end.

Keep Oracle in the demo

Run Oracle Database 23ai Free in a container so the story is "the database and ORDS stay; the application layer moves". Swapping to Postgres in the demo would make the modernization look like a data migration, which is not the point and invites the wrong questions.

Show coexistence, not a big bang

Serve one legacy APEX report through an iframe or ORDS call inside the new shell. Program managers will ask "do we lose everything on day one?" — the answer on screen should be no.

Decisions made and risks

Decided: FastAPI for the API tier

Python 3.12 + FastAPI + SQLAlchemy + python-oracledb; the same language as the ingest jobs, so one repo, one test runner, and PL/SQL-to-Python comparisons read naturally on stage.

Decided: EMT is APEX — demo is APEX-specific

Beat 5 should include a side-by-side of one APEX page process (PL/SQL in the page designer) and the equivalent FastAPI route + test, and beat 6 keeps a real APEX page running against the same Oracle schema.

Proxy data must be labelled as proxy

Public sources are not CEFMS, EMS, P2 or BUILDER data. Every tile and the leave-behind must say which internal system it stands in for; otherwise the demo invites a fidelity argument it cannot win.

USACE-owned dam condition is withheld

All 752 USACE dams in NID show condition "Not Available". Condition views will be dominated by state-regulated dams; say so on the tile, and use LPMS lock delay/unavailability as the USACE-owned "status" signal instead.

Bot-blocked hosts and one-time PDFs

usace.army.mil rejects scripted clients and work plans are PDF tables. Treat these as one-time, browser-assisted acquisitions committed as fixtures — never as live feeds in the demo.

Project ↔ contract matching is fuzzy

Work-plan projects and USAspending contracts share no key. Match by district office + state + name tokens and show a confidence flag; do not present matches as authoritative.
